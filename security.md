# ShadowTrace — Security & Privacy Model

---

## 1. Core Security Philosophy

ShadowTrace eliminates conventional authentication vulnerabilities by removing passwords, email addresses, phone number identifiers, and centralized profile databases. Security relies on hardware-backed device keys, cryptographic tokens, strict OS-level IPC boundaries, and database Row-Level Security (RLS).

---

## 2. Threat Model & Assets

### 2.1 Protected Assets
* **Raw Location Coordinates:** Current latitude, longitude, altitude, heading, and speed of group members.
* **Group Membership:** The relationship graph mapping which device identifiers belong to which group.
* **Device Private Keys:** The cryptographic secrets used to sign packets and prove membership.
* **Local Nicknames / Metadata:** Custom names given to friends by the device owner.

### 2.2 Potential Threat Actors
* **Passive Network Eavesdropper:** Attacker snooping on public Wi-Fi or cellular transit.
* **Malicious Third-Party Android App:** Colocated application on the same Android device attempting to harvest location via IPC or intent spoofing.
* **Compromised Group Participant / Rogue Device:** A legitimate group member whose device was compromised or who maliciously attempts to dump historical data.
* **Compromised Backend Infrastructure:** Attacker gaining read access to the Supabase database.

## 3. Cryptographic Device Identity

```
                    Android Device
+------------------------------------------------------+
|                 Android Keystore                     |
|                                                      |
|  +------------------------------------------------+  |
|  | Hardware-Backed Keypair (EC NIST P-256)        |  |
|  | - Private Key: NON-EXPORTABLE                  |  |
|  | - Purpose: KeyProperties.PURPOSE_SIGN          |  |
|  +-----------------------+------------------------+  |
|                          |                           |
+--------------------------|---------------------------+
                           |
            Public Key Export (X.509 DER)
                           |
                           v
            SHA-256 Digest (Hex / Base58)
                           |
                           v
            Device Identifier (`device_id`)
```

### Identity Principles:
1. **Device IDs are Identifiers, NOT Secrets:** A `device_id` is a public routing handle derived deterministically from the public key. Possession of a `device_id` alone grants zero authorization.
2. **Proof of Ownership via Signatures:** Authoritative actions (joining groups, publishing location packets) require ECDSA signatures generated by the hardware-backed private key.
3. **Hardware Isolation:** Private keys never enter heap memory as extractable byte arrays; all cryptographic operations occur inside the Android Keymaster / StrongBox TEE.

## 4. Group Authorization & Invite Security

### 4.1 Group Creation
1. Client generates a cryptographically random 128-bit `group_id` (UUID v4) and a 256-bit symmetric `invite_secret`.
2. Group metadata is recorded on the backend.

### 4.2 High-Entropy Invite Tokens
Invite QR codes and deep links contain:
```text
shadowtrace://invite?group_id=<uuid>&secret=<hex_token>&expires=<timestamp>
```
* **No Short Predictable Codes:** Group pairing never relies on 4-digit or 6-digit numeric codes that can be brute-forced.
* **Invite Expiration:** Invites support configurable TTLs (e.g. 15 minutes, 24 hours, or single-use).
* **Join Proof:** To join, the joining device sends `{group_id, invite_secret, device_id, signature}`. The backend validates the secret and registers the device in `memberships`.

## 5. IPC Security (Client ↔ Service Boundary)

Because the Client and Service are separate APKs, Android IPC (AIDL) must be hardened against unauthorized access:

```
[Unauthorized App] ──(Bind Request)──► [Service AIDL Stub]
                                              │
                                              ├─► Check Binder.getCallingUid()
                                              ├─► Verify Package Signature Certificate
                                              │   (Must match trusted Client signing key)
                                              ▼
                                         [REJECT / SECURITY EXCEPTION]
```

* **Caller Signature Verification:** On every IPC invocation, the Service inspects the caller UID via `PackageManager.checkSignatures()` to ensure the caller matches the official ShadowTrace Client certificate.
* **Non-Exported Broadcast Receivers:** All internal intents and broadcasts use explicit component names and are flagged with `android:exported="false"`.

---

## 6. Location Privacy & Data Minimization

* **Current Location Only (No History):** The backend schema uses a single upsertable record per device in `current_locations`. No historical trail or coordinate log is maintained.
* **Zero PII on Backend:** Nicknames, contact lists, and device nicknames are stored strictly inside the Client's local app storage. The backend stores only UUIDs, public keys, and timestamps.
* **Explicit Foreground Transparency:** The Service runs as an Android Foreground Service displaying a continuous, persistent notification whenever location collection is active. There is no hidden background tracking.

---

## 7. Row-Level Security (RLS) Matrix

| Table | Read Policy | Write Policy |
|---|---|---|
| `groups` | Verified members of `group_id` | Any authenticated device creator |
| `devices` | Public read (public keys only) | Device owner only |
| `memberships` | Members of the same `group_id` | Valid invite secret holder / Admin |
| `current_locations` | Members of the same `group_id` | Device owner (`device_id` matches sender) |

---

## 8. Anti-Replay & Tamper Resistance

* **Packet Timestamp & Nonce:** Every published location packet contains a millisecond timestamp and monotonic sequence counter.
* **Ingest Window:** Location packets older than 60 seconds are discarded by the ingest policy to prevent replay attacks.
